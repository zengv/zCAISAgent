## 1. 一句话定位

**做一个可私有化、可审计、可评估、可扩展的"通用 Agent 运行时"：以同一个状态机驱动检索、工具调用、代码执行、浏览器、文件操作与多步任务；Agentic RAG 是它的一个内置能力形态。**

不是"又一个知识库问答"，也不是"又一个低代码 Agent 编排器"，而是**通用能力内核 + 可复用技能包 + 产品化外壳**。

### 1.1 产品边界

| 做 | 不做（至少 MVP 不做） |
|---|---|
| 通用 Agent 多步任务（规划/工具/代码/浏览/文件） | 通用低代码工作流编排器（不替代 Dify/n8n） |
| 多源检索、证据融合与 Agentic RAG | 模型训练/微调平台 |
| 工具接入（MCP/OpenAPI/SQL/沙箱） | 全功能 BI / 数据仓库 |
| Skill 技能包、定时任务（Cron） | 通用爬虫平台 |
| 证据、引用、轨迹、评估 | 通用 IM / OA 系统 |
| 权限、审计、多租户 | 移动端原生 App |
| Python SDK + HTTP API | — |

### 1.2 关键假设（已确认，2026-11-05）

| # | 假设 | 影响 | 若不成立 |
|---|---|---|---|
| A1 | zCAISAgent 是**通用 Agent 平台**，首个参考场景为企业知识问答/研究助理 | 决定默认动作集、数据源、权限模型、UI | 若首个场景是工单/自动化，需提前启用工具与 Cron |
| A2 | **私有化/混合部署**优先 | 决定模型网关、存储、合规设计 | 若纯 SaaS，可简化部署但需强化隔离与计费 |
| A3 | 中文为主、中英混合 | 决定 embedding/rerank/分词选型 | 若多语种，需多语言模型与评测集 |
| A4 | 团队以 **Python** 为主 | 决定技术栈与目录骨架 | 若 Java/Node，端口层可保留，适配层重写 |
| A5 | 已有或可整理**黄金评估集** | 决定质量门禁可行性 | 若无，需先投入数据标注（M1 前置） |
| A6 | MVP 阶段**单机可跑、单租户可用** | 决定是否先上 K8s | 若直接多租户，需提前做 RLS 与配额 |
| A7 | 检索/RAG 是**内置能力**而非项目边界 | 决定 ActionSpace 与 Skill 设计 | 若只做 RAG，可裁剪代码/浏览/文件动作 |

> **确认状态**：以上 A1-A7 已由主人确认按建议执行。A6 采用"逻辑多租户、物理单租户"起步，避免过早分布式化；A5 的黄金评估集在 M0 同步启动标注。

## 4. 核心场景（通用能力 + 两个参考场景）

### 4.0 S0 通用任务执行（平台主场景）

| 项 | 内容 |
|---|---|
| 输入 | 一个目标 + 可用工具/数据源/文件 |
| 流程 | 分析 → 路由 → 规划 → 动作选择（检索/API/代码/浏览/文件）→ 观察 → 反思 → 继续/完成 |
| 输出 | 任务结果 + 执行轨迹 + 产物（文件/表格/链接） |
| 成功标准 | 任务成功率、有效动作次数、成本、可恢复性 |
| 失败处理 | 预算耗尽/不可恢复 → 输出阶段成果 + 未完成项 |
| 为何需要通用 Agent | 动作数量与顺序不可预知，必须运行时决策 |

### 4.1 S1 企业知识问答（L1 快路径，首个参考场景）

| 项 | 内容 |
|---|---|
| 输入 | 自然语言问题，可带文件/链接 |
| 流程 | 意图识别 → 轻改写 → 权限过滤 → 混合检索 → 重排 → 证据约束生成 → 引用绑定 → 输出 |
| 输出 | 结论 + 要点 + 引用（可点击定位）+ 置信度 + 更新时间 |
| 成功标准 | 答案正确、每条关键结论有出处、P95 ≤ 8s、单次成本 ≤ $0.005 |
| 失败处理 | 证据不足 → 明确说"没找到"，给出建议来源/关键词；不硬答 |
| 为何需要 Agentic | 需要判断"要不要查、查哪个源、够不够"；但不需要多轮规划 |

### 4.2 S2 跨源调研（L2/L3 慢路径，差异化场景）

| 项 | 内容 |
|---|---|
| 输入 | "对比/分析/调研"类复杂问题，可指定范围与时间 |
| 流程 | 意图与复杂度分析 → 子问题分解 → 多源并行检索 → 证据评分 → 缺口识别 → 补检索/调工具 → 综合 → claim 校验 → 报告 |
| 输出 | 结构化报告（结论、分点论证、对比表、引用、局限说明） |
| 成功标准 | 覆盖关键子问题、引用可追溯、不编造、P95 ≤ 60~90s、成本 ≤ $0.15 |
| 失败处理 | 预算耗尽 → 输出"阶段性结论 + 未覆盖项"，而非假装完成 |
| 为何需要 Agentic | 子问题数量不可预知；需要迭代检索与工具 |

### 4.3 S3 客服/工单副驾（V1）

结合业务 API（订单、工单、CRM）+ 知识库 + 历史会话记忆；高风险动作（退款、改单）必须 HITL 审批。

### 4.4 S4 合规/审计问答（V1）

强调：版本生效时间、条款级引用、冲突提示、完整审计日志、拒答策略。此场景**默认关闭 L3 自主模式**，只允许 L1/L2 + 人工复核。

### 4.5 S5 智能问数（NL2SQL，已交付）

| 项 | 内容 |
|---|---|
| 输入 | 自然语言数据问题，如"S1 的成绩是多少？""梁老师带的课程有哪些？" |
| 流程 | 意图/数据查询识别 → 路由到 `n2sql` → LLM 生成 SQL → 只读校验 → 行级权限注入 → 只读执行 → 自然语言归纳 |
| 输出 | 答案 + SQL + 结果表 + 数据范围标识（`scope`） |
| 成功标准 | 只读、不越权、可审计；未知用户或无权限查询 100% 拒绝 |
| 失败处理 | SQL 非法/数据库不可用/未配置数据权限 → 明确失败原因，不返回猜测数据 |
| 为何需要 Agent | "问题 → 表/列"的映射需要模型推理；但只读、表白名单与行级范围必须由运行时强制执行，不能交给模型自觉 |

## 6. 关键交互设计

### 6.1 回答卡片（所有场景统一）

```
┌──────────────────────────────────────────────────────┐
│ 结论（1-2 句，直接回答问题）                          │
│                                                      │
│ 关键要点                                             │
│ • 要点 1 [1]                                         │
│ • 要点 2 [2][3]                                      │
│                                                      │
│ 证据 [1] 《2026 差旅管理办法》P3 · 2026-03-01 生效    │
│      [2] 财务系统 / policy API · 2026-10-20 更新       │
│                                                      │
│ 置信度：高 / 中 / 低（低置信度必须说明原因）           │
│ 局限：未覆盖 XX 场景；建议补充 YY 资料                 │
│ [查看决策轨迹] [继续追问] [反馈]                      │
└──────────────────────────────────────────────────────┘
```

**硬规则**：
- 没有证据的关键结论不得展示为确定语气；要么标注"模型推断"，要么删除；
- 置信度必须由校验器产出，不允许模型自报；
- "没找到"必须给出下一步建议，而不是空白。

> 动作类任务输出（S0/S3）：状态（完成/部分完成/失败）+ 产物（文件/链接/表格）+ 执行轨迹 + 未完成项与下一步建议。

### 6.2 证据面板

- 片段高亮命中句；
- 显示来源类型、标题、更新时间、版本、权威等级、权限标记；
- 支持"仅看一手来源"过滤；
- 冲突时并排展示，标注差异点与时间。

### 6.3 轨迹抽屉（信任的核心）

| 区块 | 内容 |
|---|---|
| 决策链 | 分析 → 路由 → 规划 → 动作（检索/工具/代码/浏览/文件）→ 观察 → 反思 → 生成/执行 → 校验 |
| 每步 | 输入摘要、输出摘要、耗时、token、成本、模型 |
| 检索 | 每源 query、top-k、命中数、耗时、是否降级 |
| 校验 | 每条 claim 的支持证据、判定、理由 |
| 导出 | JSON / 分享链接（脱敏） |

> 设计原则：**轨迹是产品功能，不是调试附属品。** 它同时服务用户信任、运营排障、合规审计。

### 6.4 澄清与拒答

- 澄清：给 2-4 个可选项 + "其他"，避免开放式追问；
- 拒答：说明"缺什么"，而不是"我不能回答"；
- 越权：说明"无权限"，不泄漏文档存在性。

### 6.5 HITL 审批

高风险工具调用前弹出审批卡：动作、参数、影响范围、可撤销性、建议。支持"本次允许/始终允许/拒绝并说明"。

## 7. 指标与验收

### 7.1 北极星指标

**任务成功率（Task Success Rate）** = 达成用户目标（问答被采纳 / 动作任务完成且校验通过）的任务数 / 总任务数。回答类任务额外要求引用校验通过；动作类任务额外要求副作用审计完整。

> 不用"回答数""会话数"这类虚荣指标；也不用单纯"满意度"，因为用户会为"看起来像答案"的幻觉打高分。

### 7.2 分层指标与目标值

| 层 | 指标 | MVP 目标 | V1 目标 | 说明 |
|---|---|---|---|---|
| 质量 | 答案正确率（人工/双 judge） | ≥ 80% | ≥ 88% | 分层评估集 |
| 质量 | Faithfulness（Ragas） | ≥ 0.85 | ≥ 0.92 | 回答是否忠于证据 |
| 质量 | Citation Support（claim 有据率） | ≥ 0.85 | ≥ 0.92 | 自研 |
| 质量 | Context Recall | ≥ 0.80 | ≥ 0.88 | 检索覆盖 |
| 质量 | 拒答准确率（该拒不拒/不该拒乱拒） | ≥ 75% | ≥ 85% | 无答案集 |
| 质量 | 动作任务完成率（S0/S3） | ≥ 70% | ≥ 80% | 多步任务 |
| 轨迹 | 平均有效动作次数（L1/L2/L3） | ≤ 2 / 5 / 12 | 同左 | 越少越好；节点步数仅作预算上限 |
| 轨迹 | 无效工具/检索调用率 | ≤ 10% | ≤ 5% | 重复、错源 |
| 轨迹 | 循环未收敛率 | 0 | 0 | 预算强制 |
| 效率 | 首 token P95 | ≤ 3.0s | ≤ 2.5s | 流式 |
| 效率 | L1 完成 P95 | ≤ 10s | ≤ 8s | 单跳 |
| 效率 | L2 完成 P95 | ≤ 35s | ≤ 25s | 多跳 |
| 效率 | L3 完成 P95 | ≤ 120s | ≤ 90s | 深度 |
| 成本 | L1 单次成本 | ≤ $0.008 | ≤ $0.005 | 模型分层 |
| 成本 | L2 单次成本 | ≤ $0.05 | ≤ $0.03 | 含重排 |
| 信任 | 引用点击率 | ≥ 30% | ≥ 45% | 说明用户在看证据 |
| 信任 | 纠错率（点踩/改答案） | ≤ 8% | ≤ 5% | — |
| 系统 | 可用性 | 99.0% | 99.5% | — |
| 系统 | 索引新鲜度 | ≤ 1h | ≤ 15min | 增量 |
| 安全 | 越权召回 | 0 | 0 | 硬门槛 |
| 安全 | 注入红队通过率 | ≥ 90% | ≥ 95% | 硬门槛 |

### 7.3 验收方式

- **离线**：每次发版跑黄金集，指标不得低于基线（允许单项 -2% 但总分不得下降）；
- **在线**：影子流量 + 小流量 A/B；
- **人工**：每周抽检 50 条轨迹，校准 judge（防"评估者悖论"）；
- **拒绝**：只报平均值不报分层的评估报告。

## 8. 非功能需求

| 类别 | 要求 | 说明 |
|---|---|---|
| **性能** | 见 7.2；单实例 ≥ 20 并发任务，可水平扩展 | 检索与 LLM 调用必须异步 |
| **可用性** | MVP 99.0%，V1 99.5%；单源/单模型故障可降级 | 降级策略必须可演练 |
| **数据隔离** | 逻辑多租户（tenant_id + RLS），物理可单租户 | 越权是零容忍项 |
| **权限** | RBAC + 文档 ACL；工具 scope 分离 | 最小权限 |
| **审计** | 记录 run/step/证据/工具/审批；留存 ≥ 180 天 | 可导出 |
| **合规** | 数据不出境可配置；支持私有化模型；DSR 可删除 | 按客户要求扩展 |
| **可维护** | 配置化策略；新增源/工具不改内核 | 见 03 扩展点 |
| **可观测** | 全链路 trace + 成本指标 | 默认开启 |
| **兼容** | OpenAI 兼容模型接口；MCP 工具协议 | 避免供应商锁定 |
| **语言** | 中文优先，中英混合可用 | 评测集覆盖 |

## 9. 竞品与差异化

| 产品/方案 | 优势 | 局限 | 我们的差异 |
|---|---|---|---|
| **Dify / FastGPT / RAGFlow** | 低代码、知识库成熟、上手快 | 深度 Agent 编排弱；轨迹与评估弱；内核与 UI 耦合 | 内核可独立复用；轨迹级可审计；评估门禁 |
| **Coze / 扣子** | 生态与渠道强 | 私有化与深度定制受限 | 私有化、数据可控 |
| **LangGraph + LangSmith / LlamaIndex** | 开发者生态强、灵活 | 只是框架，无产品层；需自建权限/评估/UI | 提供产品化外壳与治理 |
| **Glean / Perplexity Enterprise** | 体验成熟、企业搜索强 | 不可深度定制；数据在第三方 | 可私有化、可接内部系统 |
| **自研 pipeline** | 完全可控 | 重复造轮子；难扩展 | 端口化 + 复用 |

**一句话差异化**：**框架无关的内核 + 证据级可审计 + 评估即门禁 + 多源工具融合。**

## 10. 部署与交付形态

| 形态 | 适用 | 说明 |
|---|---|---|
| **私有化单机** | 试点、数据敏感 | Docker Compose：API + PG + Redis + 模型网关 |
| **私有化集群** | 生产 | K8s：API/Worker 水平扩展，PG 主从，对象存储 |
| **混合云** | 中等敏感 | 数据与索引在客户侧，模型调用走专线/私有网关 |
| **SaaS 多租户** | 标准化客户 | 需强化隔离、配额、计费；MVP 不做 |

**模型策略**：默认接 OpenAI 兼容网关（可指向 vLLM/Ollama/云厂商）；embedding 与 rerank 优先本地部署，降低成本与数据外流。

## 12. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 过度自主导致成本/延迟失控 | 高 | 高 | 预算硬约束 + L0-L3 分级 + 默认 L1 |
| LLM 判断不稳定（路由/评分/校验） | 高 | 高 | 多信号融合 + 阈值校准 + 规则兜底 + 人工抽检 |
| 评估集不足导致"自我感觉良好" | 中 | 高 | M1 前置数据标注；分层集；双 judge + 人工校准 |
| 权限漏洞 | 中 | 极高 | 检索前过滤 + 结果复核 + 越权红队 + 审计 |
| 检索内容注入 | 中 | 高 | 证据/指令分区、注入检测、工具最小权限 |
| 供应商锁定 | 中 | 中 | 端口-适配器 + OpenAI 兼容 + MCP |
| 范围蔓延（既想做平台又想做应用） | 高 | 中 | 内核与参考应用分层；Studio 只做运营必需 |
| 数据质量差（文档脏、版本乱） | 高 | 高 | 解析/清洗管线 + 版本元数据 + 质量看板 |

| # | 决策 | 确认结果 | 对开发的影响 |
|---|---|---|---|
| Q1 | 首个落地场景 | **通用任务循环 + 企业知识问答作为首个内置 Skill** | M1 先打通 `plan → act → observe → reflect`；知识问答作为 Skill 验证能力层 |
| Q2 | 部署形态 | **私有化单机起步**；逻辑多租户、物理单租户；架构预留多租户 | Docker Compose 优先；表结构带 `tenant_id` + RLS；MVP 不做 SaaS 计费 |
| Q3 | 模型来源 | **混合**：生成用云/本地大模型；embedding/rerank 本地 | 统一 `LLMPort` + OpenAI 兼容网关；本地部署 embedding/rerank |

| Q5 | 语料与评估集 | **从零新建 100 条黄金集**，M0 同期启动标注 | M0 增加标注任务；M1 以该集作为门禁基线；标注规范见 03 §14 |
| Q6 | 多模态 | **不进 MVP**，V2 再做；PDF 表格解析可先支持 | 解析器优先 PDF/DOCX/HTML/MD；图片/视频 V2 |
